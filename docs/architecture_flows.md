# FHN Document Ops - Detailed Architectural Flows

To ensure accurate diagram generation in Lucidchart, the architecture is broken down into three highly detailed flows. Each step explicitly mentions the actor, the system component, and the specific database or message payload interactions.

---

## Flow 1: Internal Request Generation (The Setup)
**Purpose**: How the internal bank application initiates a secure upload request for a customer, supporting both structured (explicit document list) and unstructured (natural language) inputs.

**Actors & Systems**: 
- Bank Employee / Internal App
- FHN FastAPI Backend (Internal Routes)
- Azure Foundry (AI)
- PostgreSQL Database

**Sequence of Events**:
1. The **Internal App** sends a POST request containing customer details (Name, ID, Email) to the **FHN FastAPI Backend**. This is secured via JWT authentication.
    * *Path A (Structured)*: POST `/api/v1/internal/requests/structured` containing a strict JSON array of required documents.
    * *Path B (Unstructured)*: POST `/api/v1/internal/requests/unstructured` containing a single `request_explanation` string (e.g., "Need W2 and driver's license").
2. *If Path B (Unstructured)*: The **FHN FastAPI Backend** forwards the `request_explanation` to **Azure Foundry**. The NLP engine analyzes the text and returns a strict JSON array of mapped document types.
3. The **FHN FastAPI Backend** generates a unique GUID for the `UploadRequest`.
4. The **FHN FastAPI Backend** writes the parent `UploadRequest` to the **PostgreSQL Database** with:
    * `status` = `PENDING`
    * `request_type` = `STRUCTURED` or `UNSTRUCTURED`
    * `raw_request_explanation` = The original string (if unstructured, for auditing)
5. The **FHN FastAPI Backend** iterates through the required documents array (either provided directly or generated by Foundry) and writes child `ExpectedDocument` rows to the **PostgreSQL Database** with `status` = `PENDING`.
6. The **FHN FastAPI Backend** generates a secure frontend URL containing the GUID (e.g., `https://portal.fhn.com/upload/GUID-1234`).
7. The **FHN FastAPI Backend** returns this URL to the **Internal App**.
8. The **Internal App** distributes the secure link to the Customer via Email or SMS.

## Flow 2: Customer Document Upload (The Public Flow)
**Purpose**: How the customer securely uploads required documents and up to 3 optional supplemental documents over multiple sessions.

**Actors & Systems**: 
- Customer (Web Browser)
- FHN React SPA (Frontend Portal)
- FHN FastAPI Backend (Public Routes)
- Azure Blob Storage (or Mock Storage)
- Redis (Celery Message Broker)
- PostgreSQL Database (or Mock DB)

**Sequence of Events**:
1. The **Customer** opens the secure link in the **FHN React SPA**.
2. The **FHN React SPA** fetches the request details and pending documents from the **FHN FastAPI Backend** (`GET /api/v1/public/requests/{id}`).
3. The **Customer** drops their files into the dropzone and clicks "Submit Documents".
4. The **FHN React SPA** sends a multipart/form-data POST request (`/api/v1/public/requests/{id}/upload`). Unmapped files are explicitly tagged as `"extra"`.
5. The **FHN FastAPI Backend** validates the request. If the customer attempts to upload more than 3 extra documents, it rejects the request (HTTP 400).
6. The **FHN FastAPI Backend** streams the files directly into **Azure Blob Storage**, receiving a persistent `blob_url` in return. *(Note: If `USE_MOCK_STORAGE=True` is set for office networks, it mocks this response).*
7. The **FHN FastAPI Backend** updates the **PostgreSQL Database**:
    * Required files: Updates existing `ExpectedDocument` to `status=UPLOADED` and saves the `blob_url`.
    * Extra files: Creates a new dynamic `ExpectedDocument` row with `is_extra=True`, `status=UPLOADED`, and saves the `blob_url`.
8. For *every* uploaded file, the **FHN FastAPI Backend** enqueues an asynchronous `process_uploaded_document` task containing the `document_id` and `blob_url` into the **Redis Broker**.
9. *(Optional)* The **Customer** clicks "Finish & Lock Request". The **FHN FastAPI Backend** (`POST /finish`) verifies all required documents are uploaded, and locks the parent `UploadRequest` status to `COMPLETED`.

## Flow 3: Async Validation & Messaging (The Background Flow)
**Purpose**: How documents are processed with AI in the background, and how race-condition-free event notifications are broadcasted back to internal systems.

**Actors & Systems**: 
- Celery Worker (Python Background Process)
- Azure Document Intelligence (OCR)
- Azure Foundry (NLP Validation)
- PostgreSQL Database
- Kafka Message Broker
- Internal Bank App (Kafka Consumer)

**Sequence of Events**:
1. The **Celery Worker** continuously polls **Redis** and pops a pending document task.
2. The **Celery Worker** passes the `blob_url` to **Azure Document Intelligence** to extract raw text and key-value pairs.
3. The **Celery Worker** sends the extracted data to **Azure Foundry** to evaluate business rules, receiving a validation confidence score and `is_valid` boolean.
4. The **Celery Worker** updates the `ExpectedDocument` in the **PostgreSQL Database** to `VALIDATED` (if passed) or `FAILED` (if failed).
5. The **Celery Worker** immediately publishes a `FILE_PROCESSED` event to the **Kafka Message Broker**. This ensures the **Internal Bank App** receives the `blob_url` and validation status in real-time, on a per-file basis, regardless of success or failure (The Claim Check pattern).
6. The **Celery Worker** performs a synchronization check against the **PostgreSQL Database**:
    * Is the parent `UploadRequest` status set to `COMPLETED`?
    * Are *all* sibling `ExpectedDocuments` for this request fully processed (no docs in `PENDING`, `UPLOADED`, or `PROCESSING` states)?
7. If both conditions in Step 6 are true, the **Celery Worker** publishes a final `REQUEST_COMPLETED` event to the **Kafka Message Broker**. This includes a final `all_valid` boolean flag for the entire document package.
8. The **Internal Bank App** consumes these Kafka events to instantly update workflow dashboards for the bank employees.
